# Plan 05-02 — Reuse `JellyfinService` per profile; TTL memos; batch user data

## Why
`buildContext()` (`context.ts:300`) does `new JellyfinService(resolved.userData)` on **every** request, and `JellyfinService.getEngine()` (`service.ts:57-70`) runs `new AIOStreams(userData).initialise()` per instance. The catalog/meta/stream memos live on the instance, so a tvOS home screen (48 parallel requests) initialises 48 engines and fetches the same 24 catalogs 48 times. Logs show `"addon resources resolved"` once per request. This is the dominant cause of 10 s rows and cold-start errors.

## Steps

### 1. Service cache keyed like the user cache — `context.ts`
- `resolveUserData()` already caches `CachedUser` under `key = uuid|encryptedPassword` with `USER_CACHE_TTL_MS = 5 min` and invalidates via `JellyfinRepository.userVersions()` (lines 145-255).
- Add a `service?: JellyfinService` field to `CachedUser`. In `buildContext()`, instead of `new JellyfinService(resolved.userData)` every time:
  - Look up the cached entry for `key` (add a small exported helper `getCachedUserEntry(uuid, encryptedPassword)` or return the entry from `resolveUserData`). If `entry.service` exists, reuse it; otherwise create `new JellyfinService(entry.userData)` (the **cached** clone-source userData, not the per-request `structuredClone` copy — the engine must not capture `userData.ip`), store it on the entry, and use it.
  - When `freshCachedUser()` deletes a stale entry (version changed or TTL expired), the service goes with it — no extra invalidation logic needed.
- `ctx.service` therefore becomes shared across concurrent requests for the same profile. Confirm nothing in `JellyfinService` mutates per-request state (it does not: the only fields are the engine, init promise and memo maps).

### 2. TTL on the memos — `packages/core/src/jellyfin/service.ts`
Because the service now lives for minutes, the memo maps must not grow or serve stale data forever:
- Replace `catalogMemo`, `metaMemo`, `subtitleMemo`, `streamsMemo` (`Map<string, Promise<…>>`) with a tiny private helper `memo<T>(map, key, ttlMs, producer)` that stores `{ promise, expiresAt }`, returns the promise while `Date.now() < expiresAt`, and evicts on expiry. On producer rejection, delete the entry immediately so a transient failure is not cached.
- TTLs: catalog 60 s, meta 5 min, subtitles 5 min, streams 60 s.
- Cap each map at 2 000 entries (drop the oldest insertion when exceeded).

### 3. Batch `attachUserData` — `packages/server/src/routes/jellyfin/items.ts`
`itemFromDescriptor()` for `movie`/`series` (line 142) calls `attachUserData(ctx, [item])` per item, so `lookup()` over N ids = N DB queries. Add an optional `opts.skipUserData?: boolean` to `itemFromDescriptor`; in `library.ts` `handleItemsQuery` `Ids` branch (~line 239-247) and `itemsFromPlaystates` pass it and call `attachUserData(ctx, items)` once on the collected array. Leave `sendItem` (single item) unchanged.

### 4. Build + test + commit
- `pnpm build` zero errors; `pnpm --filter ./packages/core test` green.
- Quick manual check with `pnpm start:dev` is optional; 05-04 verifies on the VPS by grepping the container log for `addon resources resolved` counts before/after a burst.
- Commit: `perf(jellyfin): reuse JellyfinService per profile with TTL memos; batch user data lookups`; push `release`.

## Hard rules
- Do not change `USER_CACHE_TTL_MS` or the version-check logic.
- Do not make the service a global singleton across profiles — one per `uuid|encryptedPassword`.
